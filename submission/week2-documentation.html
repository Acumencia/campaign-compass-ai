Campaign Compass — Week 2 build documentation

Status: review draft, October 19, 2026. A live 30-question evaluation and AI-assisted semantic review are complete, with failures and provenance limitations recorded below. A captioned saved-live-evidence demonstration is prepared locally. Public sharing and submission remain pending.

Scope and user

Campaign Compass helps a marketer inspect a fictional brand's product, policy and campaign evidence. Week 1's dashboard and shared filters remain intact. Week 2 adds brand/product questions with source citations, source inspection and a same-question comparison of lexical search, LLM-only answers and RAG. A separate campaign-copy publishing workflow is not implemented.

Corpus and permissions

The corpus has 28 original synthetic Luma Trail documents and 119 chunks. Sources cover product specifications, brand voice, offers, shipping, claims policies, audience scenarios and fictional campaign reviews. Three historical documents provide superseded/expired hard negatives. No customer data or private company source material is included. Source metadata records provenance, owner, version, effective date, status and supersession. Content is original teaching material distributed with the MIT project; provider services keep their own terms. Fictional campaign reports must not be joined to dashboard CSV metrics.

Build and rationale

The application uses plain browser JavaScript and a loopback Node HTTP server. It retains the existing interface instead of adding a framework. Ingestion normalizes whitespace, preserves source line spans, and splits by heading with a maximum of 180 words and 30-word overlap for long sections. Short coherent sections remain short. Content hashes identify sources/chunks and bind the corpus version.

Retrieval can use local vectors with OpenAI embeddings or an existing Pinecone index. The user's selected Pinecone mode is integrated llama-text-embed-v2, 1024 dimensions, cosine, field mapping `text`. Source chunks and questions go to Pinecone for embeddings. Selected local source excerpts go to Claude or OpenAI for generation. Metadata filters exclude archived/expired sources by default; explicit historical filtering preserves status labels. Top-k defaults to five. The 0.2 similarity threshold is uncalibrated and is not confidence.

Uploads use fresh isolated namespaces and local receipts. The recorded user upload contains 119 chunks; the contemporaneous selected-namespace check observed 119/119 at 13:50:51 UTC on October 19. Index-wide totals alone are insufficient. The application validates returned chunk IDs, content hashes, corpus version and source metadata against local chunks and ignores remote replacement text.

Freshness is explicit: changed source content requires re-ingestion and matching vectors. There is no background crawler or automatic clock-based policy update. RAG now supplements vector matches with bounded local lexical coverage. There is no reranker or GraphRAG.

Prompts and answer validation

The grounded prompt treats both the question and retrieved text as untrusted evidence, prohibits executing embedded instructions, and requests structured JSON with corpusVersion, status, message and cited claims. Allowed statuses are answered, clarification and insufficient_evidence. Every answered claim requires a known supplied chunk and an exact matching source quote. Missing evidence should yield abstention, and ambiguity should yield clarification. Source/version conflicts must retain their scope.

The no-fresh-retrieval prompt also receives bounded conversation; earlier answers may appear in history. It uses the same generation adapter/output-token limit and forbids fabricated citations. The lexical arm shows excerpts and scores without pretending to generate an answer. Exact quote matching verifies text presence, not semantic entailment; manual review is required.

Changes after trying those questions

The semantic top five missed shipping terms in K08 and the tote materials section in K17. We now combine those results with up to five local keyword matches, removing duplicates and keeping their score types separate. This adds no remote search or embedding call. The existing 18,000-character context limit still applies, and the empty-vector gate still abstains. At top-k five, up to ten ordinary passages can be considered; this is wider coverage, not a claim of improved ranking at the same context size.

For explicit current-versus-old comparisons, up to two relevant archived passages may be added only when metadata links them to an active source already retrieved. They are labeled historical comparison only. Ordinary current questions exclude archives; explicit source filters are respected. The prompt asks for both the supported current value and an explanation of supported historical alternatives, without treating obsolete values as current. If history is absent, it must not invent an archive explanation. This supplies the missing historical context for K28/K29 without changing the corpus or reuploading it.

For device-fit clarifications, the app adds a request for physical length, width, thickness, units and carrying/protection needs if the model omitted them. The UI identifies this local addition. It adds no product claim or assertion of fit. The grounded prompt also asks the model to cover each requested part, including calculation inputs and shipping, while keeping ambiguity, abstention and citation rules intact.

The five original problem cases are now development regressions, not untouched test questions. Local replay confirms shipping/materials are supplied, linked archive passages are supplied, and the dimensions clarification is completed. Analogous synthetic examples test another product/policy combination, unrelated archives, explicit history filters, ambiguity, abstention, forged citations and context limits. The raw baseline and reviewed evidence are unchanged. The separately approved seven-question follow-up below records the actual revised-code outcomes, including two remaining failures. These development cases do not establish unseen accuracy.

Security and limits

The server binds to loopback, allowlists static assets, enforces origin/CSRF boundaries, limits requests and rejects arbitrary endpoints. Credentials remain in protected local plaintext key.json and are never returned to the browser. Nonsecret choices persist in ignored key.json.settings.json. Billing permissions remain session-only. No automatic upload, connection check, paid evaluation or retry occurs. This is a single-user local demonstration, not a production multi-tenant service.

Current Ask update: conversation, diagnostics and retrieval (19 October 2026)

The current UI has a dedicated Ask workspace, a visible conversation transcript, New chat, source inspection and expandable diagnostics. It sends at most four completed exchanges as untrusted context. Fresh retrieval and existing citation checks remain required; failed turns are excluded. Current source filters override earlier context. No production multi-user persistence is claimed.

A reported broad question, "do you have any waterproof products?", failed the answer contract. Its original generated response and retrieval diagnostics were not retained through the ordinary Ask HTTP error path, so the historical root cause remains unknown. It must not be described as a confirmed quotation error or as evidence that Ridgeline was approved waterproof.

The normal Ask error path now carries an allowlisted, bounded diagnostic: run ID, validation category and rule, zero-based claim/citation index, resolved query, prior-message count, source filter, and up to 24 retrieved source/chunk identifiers, similarity scores and supplied flags. The UI offers source inspection. Raw rejected output, prior conversation text, credentials and arbitrary provider errors are excluded. Validation remains fail-closed; no automatic retry or paid repair call was added.

General lexical coverage now removes conversational shopping terms such as "you", "any" and "products" rather than letting them dominate feature matching. For the reported question and adjacent phrasings, the local top five now include Ridgeline / Weather limits and Dayline / Care and price. Adjacent cotton, padded electronics and adjustable-strap regressions also pass. This is a general tokenization change, not a hard-coded waterproof answer. It adds no external calls, changes no corpus claims, and retains active-source filtering, explicit scope, the empty-vector gate and the context budget. Corpus hashes, namespace and stored embeddings remain unchanged. Lexical ranking changed, so old lexical scores are historical rather than current measurements.

The approved source wording remains: Ridgeline has no approved waterproof or water-resistance claim; Dayline resists light splashes but is not waterproof. Cotton canvas, an open tote design, or carrying a bottle do not imply a waterproof rating. Quote membership alone still does not prove semantic entailment or completeness.
